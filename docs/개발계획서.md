# 제주 안부똑똑 데이터 관리·전송 체계 구축 — 개발 계획서

> 본 문서는 과업지시서([PDF](./[과업지시서]%20제주%20안부똑똑%20데이터%20관리,%20전송체계%20구축%20용역_수정본.pdf))를 분석하여 수립한 개발 계획이다. 세부 요구사항 식별자(SFR-001~010)는 과업지시서를 따른다.

## 1. 사업 개요

| 항목 | 내용 |
|---|---|
| 사업명 | 제주 안부똑똑 데이터 관리·전송 체계 구축 용역 |
| 금액 | 13,200,000원 (부가세 포함) |
| 기간 | 2026.10.19. ~ 2026.11.13. (약 4주) |
| 발주 | 동국대학교 COSS사업단 |
| 평가 | 기술 80% + 가격 20% (기술 평점 68점 미만 부적격) |
| 대금 | 선금 50%(선금보증서) + 잔금(검수 완료 후) |

**목적**: 제주 스마트 케어 실증에서 수집되는 IoT-LED 센서 데이터를 본교 서버에 누적 관리하고, 가명처리를 거쳐 참여 대학과 공유하며, 운영 현황을 실시간으로 확인하는 데이터 관리·전송 체계를 구축한다.

## 2. 현행 환경 분석

| 구분 | 현황 |
|---|---|
| 수집 대상 | 제주 지역 대상자 가구 |
| LED 센서 | 방별(안방·거실·주방 등) 점등 기록. 점등 중 약 12초 간격 1행 기록, 소등 중 무기록. 일평균 약 4만 행(2026.6, 센서 58개 기준) |
| 전력(AMI) | 시간 단위 사용량 테이블 2종 존재하나 **미적재**. 적재 시 원시스템 운영사의 데이터 제공 필요 (→ SFR-009) |
| 원시스템 | 현장 돌봄 관리 시스템. **MariaDB 기반, 31개 테이블**. 소스·저작권은 원권리자 소유 |
| 적재 환경 | 본교 다향관 서버 |
| 누적 적재 | 단기 보관(약 3일) 구조 → 누적 구조로 전환해 운영 중 |
| 운영 대시보드 | 실시간 운영 대시보드 구축·운영 중 |

**현행 데이터 구조의 문제점** (과업 추진 배경):
1. 데이터가 테이블별로 흩어져 있어 **대상자 단위 통합 조회가 어려움**
2. 장비 상태가 **현재값만** 남아, 무활동과 장비 중단을 사후 구분하기 어려움
3. **직접식별자(이름·연락처·주소)와 자유기술 식별정보**가 운영 테이블에 함께 존재
4. 코드값·결측 표기가 **표준화되지 않음**
5. 외부 제공용 **가명처리·전송 체계가 부재**

## 3. 목표 시스템 아키텍처

```
┌──────────────┐    ┌───────────────────┐    ┌────────────────────┐
│  원시스템     │    │   누적 DB (시계열) │    │   전송용 DB (분리)  │
│ 현장 돌봄관리 │──▶ │  - 점등구간 파생   │──▶ │  가명처리 7개 테이블 │
│ MariaDB 31tbl│ETL │  - 장비상태 이력   │ETL │  (원본과 물리 분리)  │
│ (원본 보존)   │    │  - 대상자 통합뷰   │    │                    │
└──────────────┘    └─────────┬─────────┘    └──────────┬─────────┘
   (소스 수정 금지)            │                          │
                              ▼                          ▼
                    ┌───────────────────┐     ┌──────────────────────┐
                    │ 실시간 운영 대시보드│     │ MQTT Broker (pub/sub) │
                    │ (적재·센서·전송현황)│     │  TLS 암호화 전송       │
                    └───────────────────┘     └──────────┬───────────┘
                                                          ▼
                                               참여 대학 (구독형 수신)
                  ┌──────────────────────────────────────────────┐
                  │ 매핑 테이블(원↔가명): 암호화·분리보관, 발주기관 전용 │
                  └──────────────────────────────────────────────┘
```

- 핵심 원칙: **원본은 본교 서버 보존, 외부 제공은 가명처리본만**, 개인정보는 외부 클라우드 AI 입력 금지, 모든 처리는 본교 서버 내 수행.

## 4. 기술 스택 (제안, 조정 가능)

| 계층 | 선택 | 근거 |
|---|---|---|
| DB | **MariaDB** (기존 유지) | 원시스템/누적 DB가 MariaDB. 전송용 DB는 별도 스키마/인스턴스로 물리 분리 |
| ETL/파이프라인 | **Python** (스케줄: cron/systemd timer) | 파생 테이블·가명처리·재식별 시험에 적합, 무상 라이선스 |
| API | **FastAPI** (또는 기존 스택과 정합) | 전송·권한·대시보드 연계 API |
| 메시지 전송 | **Eclipse Mosquitto** (MQTT, TLS) | 표준 pub/sub, 오픈소스, 구독 권한·ACL 지원 |
| 대시보드 | **기존 대시보드 도구 활용** | 과업지시서 명시(기존 구성 재사용) |
| 가명처리 | 비밀키 기반 토큰화 + 암호화 매핑 테이블 | "단순 해시 미사용" 요구 충족 |
| SFR-010 LLM | 본교 서버 구동 **무상 라이선스 로컬 모델** 또는 규칙 기반 + 사람 검토 | 외부 AI 반출 금지 |

> 모든 도구는 **무상 라이선스 원칙**. 유상 도구 필요 시 발주기관과 사전 협의.

## 5. SFR별 구현 방안

### SFR-001 서버 진단 (필수)
- 다향관 서버의 HW(GPU 포함)·OS·DB·저장용량·네트워크·보안 설정 현황 진단.
- 데이터 누적 증가량(일 4만 행 기준) 기반 저장 용량 여유·증설 시점 산정.
- **SFR-010의 로컬 LLM 구동 가능 여부를 이 단계 진단 결과로 판단** (불가 시 규칙 기반 전환).
- 산출물: 서버 진단 보고서.

### SFR-002 누적 DB 재구조화 (필수)
- 보존 정책(압축·보관 기간·기간 경과 데이터 파기) 수립 → **보존정책서**.
- LED 원시 로그 → **점등 구간 파생 테이블**(시작 시각/종료 시각/지속 시간).
- **장비 상태 변경 이력**(정상/비활성/장애) 누적 → 무활동 구간과 장비 중단 구간 구분.
- 대상자 단위 통합 조회 구조 설계, 시각 기준 **KST 통일**.
- 산출물: DB 설계서, 보존정책서, 파생/상태 이력 적재 프로그램(소스).

### SFR-003 데이터 구조화 및 데이터 사전 (필수)
- 원시스템 테이블(31개)·필드 의미 파악 → **테이블·필드 정의서**.
- 대상자·센서·돌봄 기록·이상 알림·전력 간 **관계 정리(ERD)**.
- 코드값·결측 표기 표준화, 방별 센서 설치 현황·이상 알림 기준을 **데이터 사전**에 반영.
- 산출물: 데이터 사전, 테이블·필드 정의서.

### SFR-004 전송용 DB 분리·가명처리·전송 암호화 (필수)
- 원본과 분리된 **전송용 테이블 7개**: 대상자, 장비, 점등 구간, 장비 상태 이력, 돌봄 기록, 이상 알림, 전력 사용량(SFR-009 시). 참여 대학의 원본 DB 직접 접근 불허.
- **가명처리 기준서** 작성 → 발주기관 서면 합의 후 적용. (세부 기준은 [data-model.md](./data-model.md) 참조)
- 매핑 테이블 **암호화·분리 보관**.
- 적정성 검토 자료(기준서, 처리 결과·기록, 전송 이력) 제공.
- 전송 구간 **TLS** 암호화.
- 산출물: 가명처리 기준서, 매핑 테이블 관리 방안, 가명처리 결과·처리 기록, 전송 이력, 전송 인터페이스 정의서, 가명처리·전송 프로그램(소스).

### SFR-005 실시간 운영 대시보드 연계·확장 (필수)
- 기존 대시보드에 재구조화 누적 DB(SFR-002) + 전송 현황(SFR-006) 연계 → 적재 현황·센서 동작·전송 현황 통합 확인.
- **데이터 제공 실적(참여 대학 구독 수신 기록) 집계 화면** 포함.
- 기존 도구·구성 활용, 본교 서버 내 운영.
- 산출물: 대시보드 연계·확장분(소스).

### SFR-006 구독형 데이터 전송 체계 (필수)
- **MQTT 등 표준 pub/sub** 구조 구축.
- 참여 대학이 가명처리 전송본을 **구독 수신**, 구독 권한 관리(토픽별 ACL).
- 전송 이력 기록.
- 산출물: 전송 인터페이스 정의서, 전송 프로그램(소스), 전송 이력.

### SFR-007 권한 체계·화면 마스킹 (필수)
- 관리자 권한 **3단계**(예: 최고 관리자·일반 관리자·조회 사용자) + 화면 마스킹.
- 매핑 테이블은 **발주기관 전용 권한**으로 관리.
- 산출물: 권한 정의서.

### SFR-008 운영 이관 및 담당자 교육 (필수)
- 누적 DB·가명처리·전송·대시보드 운영 방법을 담은 **사용자·운영 매뉴얼**.
- 발주기관 담당자 대상 **교육 1회 이상** + 교육자료.
- 계정·권한·매핑 테이블·소스·설정·정기 점검 항목의 인계 절차 담은 **운영 이관 계획서**, 발주기관 단독 운영 가능 여부 확인.
- 산출물: 사용자·운영 매뉴얼, 교육자료, 운영 이관 계획서.

### SFR-009 전력(AMI) 데이터 적재·통합 (조건부)
- **발주기관이 데이터 제공을 확보한 경우에만** 수행. 미확보 시 협의 후 범위 제외.
- AMI 2종 적재 활성화 → 정본 1개로 통합 → 누적 DB 적재. 계량기 식별자 가명처리.
- 산출물: 전력(AMI) 적재 프로그램(소스).

### SFR-010 자유기술 항목 정밀 가명처리 (선택)
- 대상: 식별정보 + 식별가능정보(나이·직업·거주 묘사·가족 관계) + 특이정보(희귀 직업·병명·특이 사건).
- 처리: 삭제 / 상위 범주 일반화(나이→연령대, 날짜→월·분기) / 문장 삭제. 본인 + 메모 내 가족·동거인·보호자 동일 적용.
- **문맥 가명처리**: 남은 맥락으로 특정 가능 여부 점검, 추가 처리. 방식은 제안사 제시(사람 검토만으로도 가능). 생성형 AI 사용 시 **본교 서버 구동 무상 라이선스 모델 한정**, 서버 사양상 불가하면 규칙 기반 + 사람 검토.
- **재식별 시험**: 추론 정확 비율·한 사람으로 좁혀지는 메모 수 측정 → 재식별 시험 결과서. 본교 서버 내에서만 수행, 결과는 비율·건수로만 기록, 특정 가능 결과 발생 시 즉시 중단·파기.
- **추가 검수**: 자동 처리 후 사람 검수(전부/표본), 특이 메모 재검수 → 추가검수 기록.
- 기준: 「가명정보 처리 가이드라인」(개인정보보호위원회, 2026.3) 비정형 데이터 기준.
- 산출물: 재식별 시험 결과서, 추가검수 기록.

## 6. 공통 제약사항 (반드시 준수)
- 개인정보 포함 데이터는 본교 서버 밖 반출 금지, 외부 클라우드 AI 입력 금지.
- 원본 보존, 외부 제공은 합의 기준 가명처리본만.
- 전송본 수신 후 관리는 참여 대학 책임(발주기관-참여대학 보안 약정: 재식별 금지, 목적 외 이용·제3자 제공 금지, 종료 시 파기·통보).
- 서버 접근 계정은 수행 인력 한정, 작업 이력 기록.
- 개인정보 처리 위탁 계약 체결, 수행 인력 보안 서약서 제출.
- **원시스템 소스 수정·기능 변경은 과업 범위 제외**(읽기 전용 연계).
- 참여 대학 교육 활동용 별도 가공·분석 환경 구축은 범위 제외.
- 무상 라이선스 원칙, 본교 지정 장소 작업 원칙(원격은 승인 VPN·지정 단말).

> **크리티컬 패스**: 가명처리 기준서의 발주기관 서면 합의(W2)가 SFR-004/006의 선행 조건. W1 착수 즉시 기준서 초안을 병행 작성해 합의를 앞당긴다.
